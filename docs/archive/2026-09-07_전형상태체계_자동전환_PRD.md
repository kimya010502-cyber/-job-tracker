# 지원 현황 트래커 — 전형 상태 체계 및 자동 상태 전환 PRD

## 0. 문서 목적

본 문서는 기존 2차 개발 PRD와 별개로, **지원 내역 목록의 상태 표현 방식 개선**과 **전형 진행에 따른 자동 상태 전환 로직**을 정의한다.

핵심 목표는 다음과 같다.

1. 지원 건 전체의 진행 여부와 현재 전형의 세부 상태를 분리한다.
2. 기존 `진행중` 상태의 정보 부족 문제를 해소한다.
3. `예정 / 결과대기 / 합격 / 불합격`의 의미 중복 및 모호성을 정리한다.
4. 서류 전형에만 `서류 확인` 상태를 제공한다.
5. 특정 조건 충족 시 상태를 자동으로 `결과 대기`로 변경한다.
6. 사용자가 현재 전형 상황을 목록 화면에서 빠르게 파악할 수 있도록 한다.

---

# 1. 개선 배경

현재 지원 내역 목록에는 다음 정보가 존재한다.

- 현재 단계
- 상태

그러나 상태가 대부분 `진행중`으로 표시되어 아래 정보를 구분하기 어렵다.

- 아직 면접 전인지
- 면접을 완료하고 결과를 기다리는 중인지
- 서류를 채용 담당자가 확인했는지
- 해당 전형을 통과했는지
- 해당 전형에서 탈락했는지

따라서 본 개선에서는 아래 두 개념을 분리한다.

### A. 지원 건 전체 상태
지원 공고가 현재 살아 있는 지원인지, 종료된 지원인지 구분한다.

### B. 현재 전형 상태
서류 / 면접 / 과제 등 현재 단계에서 어떤 상태인지 상세하게 나타낸다.

---

# 2. 지원 건 전체 상태

## 2.1 목록 화면 표현

기존 `진행중` 배지를 지원 건 전체 상태로 사용하지 않는다.

대신 **기업명 왼쪽에 작은 상태 인디케이터**를 표시한다.

### 상태 종류

- 🟢 진행 중
- 🔴 종료

초기 버전에서는 2가지 상태만 사용한다.

### 예시

```text
🟢 넛지헬스케어   서비스 기획   서류       서류 확인
🟢 문토           PO           1차 면접   결과 대기
🔴 A기업          서비스 기획   서류       탈락
```

---

## 2.2 지원 건 전체 상태 계산

사용자가 별도로 수기 변경하지 않는다.

현재 전형 상태를 기반으로 시스템이 자동 계산한다.

### 진행 중

다음 상태 중 하나이면 진행 중으로 판단한다.

- 접수완료
- 서류 확인
- 진행 전
- 결과 대기
- 통과

단, `통과` 후 다음 전형이 존재하는 경우 다음 단계로 이동한 지원 건으로 처리한다.

### 종료

다음 상태이면 종료로 판단한다.

- 탈락
- 철회
- 최종 탈락
- 최종 합격

> 최종 합격은 긍정적인 결과이지만 채용 프로세스 자체는 종료된 상태이므로 초기 구현에서는 종료로 분류한다.

---

# 3. 전형 상태 체계

## 3.1 기존 상태값

기존 공통 상태값:

- 예정
- 결과대기
- 합격
- 불합격
- 지원철회

문제점:

- `예정`과 `결과대기`의 단계 차이가 직관적이지 않음
- `합격 / 불합격`은 전체 채용 결과처럼 보일 수 있음
- 면접, 과제, 서류 등 서로 다른 전형에 동일 표현을 사용하기 어려움

---

# 4. 변경된 상태값

## 4.1 서류 전형

서류 전형은 아래 상태를 사용한다.

1. `접수완료`
2. `서류 확인`
3. `결과 대기`
4. `통과`
5. `탈락`
6. `철회`

### 의미

#### 접수완료
지원서를 제출했으나 아직 채용 담당자의 확인 여부를 알 수 없는 상태.

지원 기업 최초 등록 시 기본값으로 사용한다.

#### 서류 확인
채용 담당자가 지원서 또는 이력서를 확인한 것으로 사용자가 판단한 상태.

사용자가 직접 변경한다.

서류 전형에서만 존재한다.

#### 결과 대기
서류 확인 이후 결과 발표를 기다리는 상태.

수기 변경 가능하며, 자동 변경 조건도 제공한다.

#### 통과
서류 전형을 통과하고 다음 전형으로 진행 가능한 상태.

#### 탈락
서류 전형에서 채용 절차가 종료된 상태.

#### 철회
사용자가 지원을 자발적으로 중단한 상태.

---

## 4.2 면접 / 과제 / 임원 면접 / 사용자 정의 전형

공통 상태값:

1. `진행 전`
2. `결과 대기`
3. `통과`
4. `탈락`
5. `철회`

### 의미

#### 진행 전
해당 전형이 아직 진행되지 않은 상태.

전형 예정일이 등록되어 있어도 전형을 실제로 완료하기 전에는 `진행 전`을 유지한다.

#### 결과 대기
면접, 과제 등 해당 전형을 완료하고 결과 발표를 기다리는 상태.

#### 통과
현재 전형을 통과한 상태.

다음 전형이 존재하는 경우 다음 단계로 진행한다.

#### 탈락
현재 전형에서 채용 절차가 종료된 상태.

#### 철회
사용자가 지원을 중단한 상태.

---

## 4.3 최종 결과 단계

최종 결과 단계에서는 아래 상태를 사용한다.

1. `결과 대기`
2. `최종 합격`
3. `최종 탈락`
4. `철회`

# 7. 자동 상태 전환 기능

## 7.1 목적

사용자가 모든 전형 상태를 매번 수동으로 업데이트하지 않아도 실제 채용 흐름에 맞게 일정 시점 이후 상태가 자동 변경되도록 한다.

자동 상태 전환은 두 가지 조건을 우선 지원한다.

1. `서류 확인` 후 3일 경과
2. 기록한 면접일 경과

---

# 8. 서류 확인 → 결과 대기 자동 전환

## 8.1 기본 동작

사용자가 서류 전형 상태를:

```text
접수완료 → 서류 확인
```

으로 변경하면 시스템은 `서류 확인일`을 기록한다.

### 기록 필드

```text
document_checked_at
```

기본값:

```text
상태를 서류 확인으로 변경한 시각
```

---

## 8.2 자동 전환 조건

`document_checked_at` 기준 **3일 후**에도 서류 상태가 `서류 확인`이면 자동으로:

```text
서류 확인 → 결과 대기
```

로 변경한다.

### 예시

```text
09월 04일 14:00
서류 확인으로 변경

↓

09월 07일 14:00 이후

결과 대기로 자동 변경
```

---

## 8.3 예외 조건

3일이 지나기 전에 사용자가 아래 상태 중 하나로 변경했다면 자동 변경하지 않는다.

- 결과 대기
- 통과
- 탈락
- 철회

즉, 자동 전환은 현재 상태가 여전히 정확히 `서류 확인`일 경우에만 수행한다.

---

## 8.4 서류 확인일 수정

사용자가 `document_checked_at`을 수정하면 자동 전환 기준일도 수정된 날짜를 기준으로 다시 계산한다.

예:

```text
기존 서류 확인일: 09.04
사용자가 수정: 09.02

→ 결과 대기 자동 전환 기준 = 09.05
```

---

# 9. 면접일 이후 → 결과 대기 자동 전환

## 9.1 적용 대상

면접 성격의 전형에 적용한다.

기본 적용 대상:

- 1차 면접
- 2차 면접
- 일반 면접
- 임원 면접
- 컬처핏 면접

향후 사용자 정의 단계에도 `면접형 전형` 여부를 지정할 수 있도록 확장 가능하다.

---

## 9.2 기본 동작

사용자가 면접일을 입력한다.

예:

```text
면접일
2026.09.10 14:00
```

면접 전 상태:

```text
진행 전
```

면접 일정이 지난 뒤에도 현재 상태가 `진행 전`이면 자동으로:

```text
진행 전 → 결과 대기
```

로 변경한다.

---

## 9.3 날짜만 입력한 경우

시간 입력 없이 날짜만 기록된 경우, 해당 날짜가 종료된 뒤 자동 전환한다.

예:

```text
면접일: 2026.09.10
```

자동 전환 기준:

```text
2026.09.11 00:00 이후
```

또는 시스템 구현 방식에 따라 `면접일 종료` 기준으로 판단한다.

---

## 9.4 날짜 + 시간 입력한 경우

면접 시간이 존재하는 경우 해당 시간이 지난 후 자동 전환할 수 있다.

예:

```text
2026.09.10 14:00
```

14:00 이후 상태가 여전히 `진행 전`이면:

```text
결과 대기
```

로 자동 변경한다.

### 권장 UX

면접 종료 시간을 별도로 입력하지 않으므로, 실제 면접이 진행 중인 시간에 상태가 바로 변경되는 것을 피하기 위해 **면접 시작 시간 + 일정 유예 시간**을 둘 수 있다.

초기 권장값:

```text
면접 시작 시간 + 2시간
```

예:

```text
면접 14:00
→ 16:00 이후 결과 대기
```

단, 구현 복잡도를 낮추고 싶다면 날짜 단위 전환으로 먼저 구현해도 된다.

---

# 10. 자동 전환 우선순위

자동 변경은 사용자의 수기 상태를 절대로 덮어쓰지 않는다.

### 자동 변경 허용

```text
서류 확인 → 결과 대기
진행 전 → 결과 대기
```

### 자동 변경 금지

이미 사용자가 다음 상태로 변경한 경우:

- 결과 대기
- 통과
- 탈락
- 철회
- 최종 합격
- 최종 탈락

자동 로직은 아무 작업도 수행하지 않는다.

---

# 11. 자동 상태 변경 기록

자동으로 상태가 변경된 경우 내부적으로 변경 이력을 남기는 것을 권장한다.

예시 데이터:

```text
status_changed_at
status_change_source
```

### status_change_source

가능한 값:

```text
manual
automatic
```

예:

```text
상태: 결과 대기
변경일: 2026.09.07
변경 방식: automatic
```

현재 UI에서 이 정보를 반드시 노출할 필요는 없으나, 추후 디버깅과 상태 이력 기능을 위해 저장을 권장한다.

---

# 12. 자동 상태 전환 구현 방식

## 12.1 중요한 요구사항

브라우저가 열려 있을 때만 작동하는 JavaScript `setTimeout` 방식에 의존하지 않는다.

사용자가 며칠 동안 서비스에 접속하지 않아도 다음 접속 시 상태가 정확해야 한다.

---

## 12.2 1차 권장 구현

MVP 수준에서는 **데이터 조회 시점에 자동 전환 조건을 검사하는 방식**을 권장한다.

예:

사용자가 로그인하거나 지원 내역 페이지를 열 때:

1. 현재 사용자의 진행 중 전형 조회
2. 자동 전환 조건 검사
3. 조건을 충족하는 상태 업데이트
4. 업데이트된 데이터 표시

### 장점

- 별도의 스케줄링 서버 없이 구현 가능
- 현재 Supabase 구조에 비교적 쉽게 추가 가능
- Git 기반 기존 배포 구조 유지 가능

---

## 12.3 향후 개선

서비스 규모가 커지면 Supabase scheduled function / cron 등을 사용하여 서버 측에서 주기적으로 상태를 업데이트할 수 있다.

하지만 초기 구현에서는 필수 아님.

# 13. 자동 상태 전환 의사코드

## 13.1 서류 전형

```javascript
if (
  stage.type === "document" &&
  stage.status === "DOCUMENT_CHECKED" &&
  now >= documentCheckedAt + 3days
) {
  stage.status = "WAITING_RESULT";
}
```

---

## 13.2 면접 전형

```javascript
if (
  stage.type === "interview" &&
  stage.status === "BEFORE_STAGE" &&
  now >= interviewAutoTransitionTime
) {
  stage.status = "WAITING_RESULT";
}
```

# 20. Claude 구현 지시사항

아래 내용을 Claude에 함께 전달한다.

```text
기존 UI 전체를 새로 리팩터링하지 말고,
현재 지원 내역 화면과 데이터 구조를 최대한 유지하면서
상태 체계만 확장/교체해줘.

핵심 변경:

1. 기존 목록의 "진행중" 상태 배지를 제거한다.
2. 기업명 왼쪽에 지원 건 전체 상태 인디케이터를 추가한다.
   - 초록: 진행 중
   - 빨강: 종료

3. 현재 상태 컬럼에는 현재 전형의 세부 상태를 표시한다.

서류:
- 접수완료
- 서류 확인
- 결과 대기
- 통과
- 탈락
- 철회

그 외 전형:
- 진행 전
- 결과 대기
- 통과
- 탈락
- 철회

최종 결과:
- 결과 대기
- 최종 합격
- 최종 탈락
- 철회

4. "합격 / 불합격" 문구는 중간 전형에서는
   "통과 / 탈락"으로 변경한다.

5. 서류 확인 상태로 변경하면
   document_checked_at을 자동 기록한다.

6. 서류 확인 상태가 3일간 유지되면
   결과 대기로 자동 변경한다.

7. 면접형 전형에서 면접일이 지나고
   상태가 여전히 진행 전이면 결과 대기로 자동 변경한다.

8. 자동 변경은 사용자가 이미 수기로
   결과 대기 / 통과 / 탈락 / 철회 등으로 변경한 상태를
   절대로 덮어쓰지 않는다.

9. 자동 상태 전환은 브라우저 setTimeout에 의존하지 않는다.
   우선 로그인 또는 지원 내역 조회 시
   만료 조건을 검사해서 DB를 업데이트하는 방식으로 구현한다.

10. 전형 이름 문자열이 아닌 stage_type을 기준으로
    서류/면접 자동 로직을 적용한다.

11. 기존 검색, 필터, 통계, 상세 페이지,
    사용자 정의 전형 단계 기능을 깨뜨리지 않는다.
```

# 21. 완료 기준

다음 조건을 모두 만족하면 본 개선안 구현 완료로 판단한다.

- 기업명 왼쪽에 진행/종료 상태 인디케이터 표시
- 기존 `진행중` 배지 제거
- 전형 상태값 체계 변경 완료
- 서류에서만 `서류 확인` 선택 가능
- 서류 최초 기본 상태는 `접수완료`
- 다른 전형의 최초 기본 상태는 `진행 전`
- 중간 전형 결과 표현이 `통과 / 탈락`으로 변경됨
- 서류 확인 날짜 자동 저장
- 서류 확인 3일 후 결과 대기 자동 전환
- 면접일 경과 후 결과 대기 자동 전환
- 수기 변경 상태를 자동 로직이 덮어쓰지 않음
- 자동 상태 변경 후 목록 및 상세 화면에 동일하게 반영
- 상태 변경으로 인해 단계별 합격률이 잘못 계산되지 않음
- 기존 지원 데이터와 호환되도록 migration 또는 상태값 변환 처리
