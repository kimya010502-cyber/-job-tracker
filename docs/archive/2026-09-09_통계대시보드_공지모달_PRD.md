# CatchPass — 대시보드 데이터 구성 및 신규 기능 공지 노출 PRD

## 0. 문서 목적

본 문서는 `전형 카테고리 고정 및 단계 잠금 로직 PRD` 구현 완료 이후 이어서 진행할 후속 개발 항목을 정의한다.

본 PRD의 범위는 다음 두 가지다.

1. **통계 탭의 대시보드 데이터 구조 및 노출 순서 개선**
2. **로그인 후 신규 기능 업데이트 공지 모달 노출**

본 작업은 전형 카테고리 표준화 및 단계 잠금 로직이 정상 구현된 이후 진행한다.

---

# 1. 개발 선행 조건

본 PRD는 아래 항목이 먼저 완료되었다는 전제하에 진행한다.

- 전형 카테고리 표준화 완료
- `stage_category` 데이터 정상 저장
- 기존 전형 데이터 마이그레이션 완료
- 앞 전형 미통과 시 뒤 전형 잠금 완료
- 현재 단계 계산 로직 수정 완료
- 기존 잘못된 뒤 전형 데이터로 현재 단계가 이동하지 않도록 수정 완료

통계는 반드시 `display_name`이 아니라 `stage_category`를 기준으로 집계한다.

---

# 2. 메인 화면과 통계 탭 역할 분리

## 2.1 메인 화면

메인 화면은 **현재 상황과 이번 달 기준 요약 정보**만 제공한다.

상단 KPI는 아래 4개로 고정한다.

1. 이번 달 지원
2. 진행 중
3. 이번 달 불합격
4. 최종 합격

메인에서는 누적 통계, 월별 추이, 전형 통과율 등 분석형 데이터를 제외한다.

---

## 2.2 통계 탭

통계 탭은 **누적 데이터와 지원 패턴 분석**을 제공한다.

노출 순서는 아래와 같이 고정한다.

1. 전체 지원 현황
2. 월별 지원 추이
3. 전형 통과율
4. 전형 소요시간
5. 지원 포지션 분석

각 카테고리는 하나의 큰 데이터 박스로 구분한다.

---

# 3. 통계 탭 전체 구조

```text
[통계]

1. 전체 지원 현황
   └ KPI 4개

2. 월별 지원 추이
   └ 최근 3개월 라인차트
   └ 최근 3개월 총 지원
   └ 전월 동기간 대비

3. 전형 통과율
   └ 표준 전형별 통과율

4. 전형 소요시간
   └ 표준 전형별 평균 소요시간

5. 지원 포지션 분석
   └ 포지션별 지원 수
   └ 포지션별 서류 통과율
```

---

# 4. 전체 지원 현황

## 4.1 목적

사용자가 지금까지의 누적 지원 성과를 빠르게 확인할 수 있도록 한다.

## 4.2 노출 방식

큰 박스 안에 KPI 카드 4개를 배치한다.

### 총 지원

의미:

```text
현재 사용자 계정에 등록된 전체 지원 기록 수
```

예:

```text
총 지원
47건
```

---

### 진행 중

의미:

```text
현재 채용 프로세스가 종료되지 않은 지원 건수
```

진행 중 판단 기준:

- 접수완료
- 서류 확인
- 진행 전
- 결과 대기
- 통과 후 다음 단계 존재

종료 판단 기준:

- 탈락
- 철회
- 최종 합격
- 최종 탈락

---

### 누적 탈락

의미:

```text
전체 기간 중 어느 전형에서든 탈락으로 채용 프로세스가 종료된 지원 건수
```

---

### 최종 합격

의미:

```text
최종 결과가 최종 합격으로 기록된 지원 건수
```

---

# 5. 월별 지원 추이

## 5.1 목적

최근 지원량 변화와 지원 활동 페이스를 확인한다.

## 5.2 노출 방식

최근 3개월 데이터를 **라인차트**로 제공한다.

예:

```text
7월  11건
8월  14건
9월   8건
```

현재 월이 진행 중이어도 실제 누적 건수를 그대로 표시한다.

---

## 5.3 최근 3개월 총 지원

라인차트 상단 또는 우측 보조 KPI로 표시한다.

예:

```text
최근 3개월 지원
33건
```

---

## 5.4 전월 동기간 대비

현재 월과 전월의 **동일 날짜 구간**을 비교한다.

예:

현재 날짜:

```text
2026.09.09
```

비교 기간:

```text
2026.09.01 ~ 2026.09.09
vs
2026.08.01 ~ 2026.08.09
```

계산식:

```text
(이번 달 동기간 지원 수 - 전월 동기간 지원 수)
÷ 전월 동기간 지원 수
× 100
```

표시 예:

```text
전월 동기간 대비
▲ 37.5%
```

감소 시:

```text
▼ 18.2%
```

전월 동기간 지원 수가 0건일 경우 `%` 계산 대신 아래처럼 표시한다.

```text
전월 동기간 0건
```

또는:

```text
비교 데이터 없음
```

0으로 나누는 계산은 하지 않는다.

---

# 6. 전형 통과율

## 6.1 명칭

기존 `전형별 성과` 명칭을 사용하지 않는다.

카테고리 제목:

```text
전형 통과율
```

`가장 많이 탈락한 단계` 데이터는 노출하지 않는다.

---

## 6.2 노출 대상

기본 통과율 카테고리:

- 서류
- 1차 면접
- 2차 면접
- 과제 전형
- 임원 면접

필요 시:

- 최종 합격률

`처우 협의`는 기본 통과율 카드에서 제외한다.

`CUSTOM` 전형 역시 기본 통과율 카드에서는 제외한다.

---

## 6.3 계산 방식

```text
통과율 =
통과 건수
÷
(통과 건수 + 탈락 건수)
× 100
```

분모 포함:

- 통과
- 탈락

분모 제외:

- 접수완료
- 서류 확인
- 진행 전
- 결과 대기
- 철회

---

## 6.4 노출 방식

각 전형을 작은 카드 또는 progress bar 카드 형태로 표시한다.

예:

```text
서류
42%
8 / 19
```

```text
1차 면접
50%
4 / 8
```

결과 확정 데이터가 없는 경우:

```text
-
0 / 0
```

또는:

```text
데이터 없음
```

---

# 7. 전형 소요시간

## 7.1 목적

회사마다 전형 순서가 달라도 각 전형 자체의 결과 소요시간을 비교할 수 있도록 한다.

중요:

> 앞 단계와 다음 단계 사이의 시간을 계산하지 않는다.

반드시 `stage_category`별 자체 소요시간을 계산한다.

---

## 7.2 서류

대표 지표:

```text
지원일 → 서류 결과일
```

예:

```text
서류
평균 5.4일
```

보조 지표를 제공할 수 있다.

```text
서류 확인까지 평균 1.8일
```

---

## 7.3 1차 면접

```text
1차 면접일 → 1차 면접 결과일
```

예:

```text
1차 면접
평균 2.6일
```

---

## 7.4 2차 면접

```text
2차 면접일 → 2차 면접 결과일
```

---

## 7.5 과제 전형

기본 계산:

```text
과제 제출일 → 과제 결과일
```

---

## 7.6 임원 면접

```text
임원 면접일 → 임원 면접 결과일
```

---

## 7.7 처우 협의

```text
처우 협의 시작일 → 최종 확정일
```

단, 해당 날짜 구조가 구현되지 않은 경우 데이터 필드 추가가 필요하다.

---

## 7.8 데이터 노출 정책

데이터가 없는 경우:

```text
-
```

1건만 존재하는 경우:

```text
3일
데이터 1건
```

2건 이상 존재하는 경우:

```text
평균 3.4일
데이터 6건
```

표본 수를 함께 보여주는 것을 권장한다.

---

# 8. 지원 포지션 분석

## 8.1 목적

어떤 포지션에 많이 지원했고 어떤 포지션에서 서류 성과가 좋은지 확인한다.

큰 박스를 좌우 2개 영역으로 구성한다.

---

## 8.2 포지션별 지원 수

노출 방식:

- 가로 막대그래프
- 또는 랭킹 리스트

예:

```text
서비스 기획  21건
PO           12건
PM            6건
```

지원 수 기준 내림차순 정렬.

---

## 8.3 포지션별 서류 통과율

계산:

```text
해당 포지션의 서류 통과
÷
(해당 포지션의 서류 통과 + 서류 탈락)
× 100
```

예:

```text
서비스 기획  43%
PO           38%
PM           50%
```

---

## 8.4 자유 입력 포지션 관련

현재 지원 포지션은 자유 입력을 유지한다.

따라서 아래 값이 별도 집계될 수 있다.

```text
서비스기획
서비스 기획
서비스 기획자
```

본 PRD에서는 자동 정규화하지 않는다.

향후 포지션 카테고리 표준화 기능으로 개선 가능하다.

---

# 9. 통계 데이터 새로고침

통계 페이지 진입 시 최신 DB 데이터를 기준으로 계산한다.

권장 동작:

```text
통계 페이지 진입
→ 최신 지원 데이터 fetch
→ 통계 계산
→ 렌더링
```

지원 기록 수정/삭제 후 통계 화면으로 돌아오면 최신 값이 반영되어야 한다.

---

# 10. 반응형 통계 UI

PC 우선 구현하되 모바일에서도 정상 확인 가능하도록 구성한다.

## PC

- 전체 지원 현황: 4열 KPI
- 전형 통과율: 가로 카드
- 포지션 분석: 좌우 2단
- 라인차트: 전체 폭

## 모바일

- KPI: 2 × 2
- 통과율: 세로 스택 또는 가로 스크롤
- 포지션 분석: 세로 배치
- 라인차트: 모바일 폭에 맞춰 responsive

---

# 11. 신규 기능 공지 모달

## 11.1 목적

신규 기능 및 주요 업데이트를 로그인 사용자에게 적극적으로 알린다.

공지사항은 로그인 화면 내부에 삽입하지 않는다.

**로그인 성공 후 메인 화면 진입 시 릴리즈 노트형 모달로 노출한다.**

---

# 12. 공지 모달 노출 시점

동작 순서:

```text
로그인 성공
↓
사용자 데이터 로드
↓
신규 업데이트 공지 여부 확인
↓
새 공지가 있으면 모달 노출
↓
사용자 선택
↓
메인 화면 사용
```

로그인 전에는 노출하지 않는다.

---

# 13. 공지 모달 UI

일반 경고 alert 스타일이 아니라 **릴리즈 노트형 모달**을 사용한다.

구성:

```text
[업데이트 소식]

새로워진 CatchPass를 확인해보세요

더 편리한 지원 관리를 위해
새로운 기능을 준비했어요.

업데이트 버전
v0.x.x

업데이트 일시
YYYY년 MM월 DD일 HH:mm

[업데이트 항목 1]
짧은 설명

[업데이트 항목 2]
짧은 설명

[업데이트 항목 3]
짧은 설명

[다시 보지 않기] [확인했어요]
```

---

# 14. 공지 모달 버튼

닫기 `X` 버튼은 사용하지 않는다.

하단에 두 가지 액션만 제공한다.

---

## 14.1 확인했어요

동작:

- 현재 모달 닫기
- 이번 로그인 세션에서는 재노출하지 않음
- 다음 로그인 시 동일 업데이트 공지가 다시 노출될 수 있음

즉:

```text
session dismiss
```

---

## 14.2 다시 보지 않기

동작:

- 현재 모달 닫기
- 해당 업데이트 버전을 사용자가 확인 제외 처리
- 동일 버전은 이후 로그인에서도 재노출하지 않음
- 새 버전의 업데이트 공지가 등록되면 다시 노출

예:

```text
hidden_update_version = "0.4.0"
```

현재 버전:

```text
0.4.0
```

이면 미노출.

추후:

```text
current_update_version = "0.5.0"
```

으로 변경되면 다시 노출.

---

# 15. 공지 데이터 구조

초기 구현에서는 공지 데이터를 코드 내부 상수로 관리해도 된다.

예:

```ts
const RELEASE_NOTE = {
  version: "0.4.0",
  updatedAt: "2026-09-09T16:49:00+09:00",
  title: "새로워진 CatchPass를 확인해보세요",
  description: "더 편리한 지원 관리를 위해 새로운 기능을 준비했어요.",
  items: [
    {
      title: "서류 확인 상태가 추가됐어요",
      description: "서류 전형에서 채용 담당자의 확인 여부를 기록할 수 있어요."
    },
    {
      title: "결과 대기로 자동 전환돼요",
      description: "서류 확인 후 일정 기간이 지나면 결과 대기로 자동 변경돼요."
    },
    {
      title: "면접 일정 이후 상태도 자동으로",
      description: "등록한 면접일이 지나면 해당 전형을 결과 대기로 변경해요."
    }
  ]
};
```

공지 수정 시 버전 및 업데이트 일시를 함께 변경한다.

---

# 16. 사용자별 공지 상태 저장

사용자 계정별로 아래 값을 저장하는 것을 권장한다.

예:

```text
hidden_update_version
```

또는 별도 사용자 설정 테이블:

```text
user_id
hidden_update_version
updated_at
```

`확인했어요`는 DB 저장이 필요하지 않다.

세션 상태로만 관리한다.

`다시 보지 않기`만 사용자 계정 DB에 저장한다.

# 17. 첫 공지 문구 예시

## 제목

```text
새로워진 CatchPass를 확인해보세요
```

## 소개

```text
더 편리한 지원 관리를 위해
새로운 기능과 개선사항을 준비했어요.
```

# 20. Claude 구현 지시사항

```text
전형 카테고리 고정 및 단계 잠금 로직 구현이 끝난 현재 프로젝트를 기준으로
메인 KPI, 통계 탭, 신규 업데이트 공지 모달을 수정해줘.

[메인]

지원 내역 메인 상단 KPI:
- 이번 달 지원
- 진행 중
- 이번 달 불합격
- 최종 합격

메인에 누적 총 지원, 전형 통과율 그래프 등 분석 데이터는 넣지 않는다.

[통계]

통계 탭의 데이터 박스 순서:

1. 전체 지원 현황
2. 월별 지원 추이
3. 전형 통과율
4. 전형 소요시간
5. 지원 포지션 분석

전형 데이터는 display_name이 아니라 stage_category 기준으로 계산한다.

월별 지원 추이는 최근 3개월 라인차트로 구현한다.

전월 비교는 전체 월 기준이 아니라
현재 날짜까지의 전월 동기간과 비교한다.

예:
9월 1~9일 vs 8월 1~9일

전형 통과율:
통과 / (통과 + 탈락)

전형 소요시간은 회사별 전형 순서가 아니라
각 stage_category 자체의 진행일/결과일 기준으로 계산한다.

[공지]

로그인 성공 후 메인 진입 시 신규 버전 업데이트 공지를
릴리즈 노트 스타일 중앙 모달로 노출한다.

X 닫기 버튼은 만들지 않는다.

하단 버튼:
- 다시 보지 않기
- 확인했어요

확인했어요:
현재 로그인 세션에서만 닫는다.

다시 보지 않기:
현재 업데이트 버전을 사용자 계정에 저장하고
같은 버전 공지는 이후 로그인에서 다시 노출하지 않는다.

새 업데이트 버전이 등록되면 다시 노출한다.

공지에는 반드시 아래 데이터를 제공한다.
- 업데이트 제목
- 업데이트 버전
- 업데이트 일시
- 핵심 업데이트 항목 2~4개

기존 인증, 지원 CRUD, 검색, 필터, 자동 상태 전환,
단계 잠금, 중복 지원 경고 기능을 깨뜨리지 않는다.
```

# 22. 신규 기능 공지 모달 — 디자인 상세 가이드

본 섹션은 앞서 제작한 **CatchPass 릴리즈 노트형 업데이트 모달 목업**의 시각적 구조를 참고하여 실제 UI를 구현하기 위한 상세 디자인 기준을 정의한다.

목표는 일반 경고창이 아니라 **업데이트 내용을 보기 좋게 정리한 릴리즈 노트 카드**처럼 보이도록 하는 것이다.

## 22.1 전체 레이아웃

### 기본 형태

- 화면 중앙 정렬 모달
- 배경은 전체 화면 dim 처리
- 메인 화면은 뒤에서 보이되 콘텐츠 집중을 위해 어둡게 처리
- 모달은 세로형 카드 구조
- 상단 소개 → 버전/업데이트 일시 → 주요 업데이트 목록 → 하단 버튼 순서
- 닫기 `X` 버튼은 제공하지 않음

### 권장 크기 — PC

```text
width: 680 ~ 760px
max-height: 85vh
```

내용이 길어질 경우:

```text
modal 내부 body 영역만 vertical scroll
footer button 영역은 하단 고정 가능
```

### 모바일

```text
width: calc(100vw - 32px)
max-width: 100%
max-height: 90vh
```

PC용 모달을 단순 축소하지 말고 모바일에서는 카드 간격과 텍스트 크기를 재조정한다.

# 23. 모달 배경 처리

모달이 열렸을 때 기존 화면은 유지하되 사용자의 시선을 공지에 집중시킨다.

권장:

```text
background overlay:
rgba(15, 23, 42, 0.45 ~ 0.58)
```

선택적으로 아주 약한 blur 적용 가능:

```text
backdrop-filter: blur(2px ~ 4px)
```

과한 blur는 사용하지 않는다.

# 36. 닫기 동작 제한

다음 방식으로는 모달을 닫지 않는 것을 기본 정책으로 한다.

- X 버튼 없음
- dim background 클릭으로 닫기 없음

사용자는 반드시 아래 둘 중 하나를 선택한다.

```text
확인했어요
다시 보지 않기
```

`ESC` 키는 접근성 측면에서 닫을 수 있도록 허용할지 선택 가능하나,
허용할 경우 `확인했어요`와 동일한 세션 dismiss로 처리한다.

초기 구현 권장:

```text
ESC = 확인했어요와 동일 동작
```

# 40. Claude용 디자인 구현 지시사항

```text
로그인 후 노출되는 업데이트 공지 모달은
일반 Alert/Dialog 형태가 아니라
"Release Notes / What's New" 형태의 정보형 모달로 디자인해줘.

앞서 제작한 CatchPass 목업의 구조를 참고해서 다음 순서를 유지한다.

1. 상단 작은 "업데이트 소식" 배지
2. 큰 제목 "새로워진 CatchPass를 확인해보세요"
3. 1~2줄 소개 문구
4. 버전 / 업데이트 일시를 보여주는 연한 배경의 정보 영역
5. 업데이트 기능 3~4개를 아이콘 + 제목 + 설명 형태의 카드 목록으로 노출
6. 하단에 "다시 보지 않기" / "확인했어요" 버튼 제공

디자인 원칙:
- CatchPass의 muted blue-purple 계열 포인트 컬러 사용
- 따뜻한 느낌의 저채도 블루/라벤더 사용
- 흰색 배경 중심
- 과한 gradient 사용하지 않기
- glassmorphism 사용하지 않기
- 카드마다 강한 shadow 사용하지 않기
- 지나치게 AI SaaS 템플릿처럼 보이지 않도록 타이포그래피와 구분선 중심으로 정리
- 아이콘은 작고 단순하게
- 일러스트는 선택 사항이며 UI보다 강조되지 않도록
- 모달 외부 배경은 dim 처리
- X 닫기 버튼 없음
- overlay 클릭으로 닫기 없음

PC:
- 약 680~760px 폭
- 중앙 배치

모바일:
- 화면 좌우 16px 여백
- 업데이트 카드 세로 배치
- CTA 버튼은 모바일에서 세로 배치 가능

모달 콘텐츠가 길면 모달 body만 스크롤되도록 구현해줘.

공지 데이터는 UI 코드에 직접 하드코딩하기보다
releaseNotes 데이터 객체와 렌더링 컴포넌트를 분리해서
다음 업데이트 때 데이터만 교체할 수 있게 만들어줘.
```

# 41. 디자인 완료 기준

- 일반 확인 팝업이 아니라 Release Note 형태로 보임
- 제목 / 업데이트 일시 / 기능 변경 내용의 정보 위계가 명확함
- 신규 기능 3~4개를 빠르게 스캔 가능
- PC 화면에서 과도하게 크거나 작지 않음
- 모바일에서 잘림 없이 확인 가능
- 업데이트 내용이 많아져도 내부 스크롤 가능
- X 버튼 없음
- overlay 클릭으로 닫히지 않음
- 다시 보지 않기 / 확인했어요 두 동작이 구분됨
- 기존 CatchPass 디자인 톤과 자연스럽게 연결됨
- 공지 버전 변경 시 UI 수정 없이 데이터 변경만으로 신규 공지 노출 가능
