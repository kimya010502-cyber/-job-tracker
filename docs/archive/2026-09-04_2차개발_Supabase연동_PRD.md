# 지원 현황 트래커 2차 개발 PRD

## 0. 문서 목적

본 문서는 기존 **지원 현황 트래커 1차 MVP**를 기반으로 진행하는 **2차 개발 요구사항**을 정의한다.

현재 개발 환경은 다음을 전제로 한다.

- 로컬 개발: VS Code
- 개발 보조: Claude
- 버전 관리: Git
- 배포 방식: Git 저장소에 push 후 배포
- 기존 데이터 저장: 브라우저 Local Storage 중심
- 2차 개발 목표:
  1. 서류 전형 상태값 확장
  2. 브라우저/기기 간 데이터 동기화
  3. 이메일 + 비밀번호 기반 사용자 인증
  4. 기존 Local Storage 데이터의 계정 데이터 마이그레이션
  5. 추후 배포 확장을 고려한 기본 사용자 데이터 구조 마련

---

# 1. 2차 개발 핵심 목표

## 1.1 서류 전형 상태값 개선

현재 모든 전형 공통 상태값은 다음과 같다.

- 결과대기
- 합격

3. 결과대기
4. 합격
5. 불합격
6. 지원철회

### 그 외 전형 상태값

1. 예정
2. 결과대기
3. 합격
4. 불합격
5. 지원철회

## 1.2 브라우저/기기 간 데이터 연동

현재 Local Storage 기반 저장 방식은 동일한 브라우저에서만 데이터 유지가 가능하다.

2차 개발에서는 사용자 계정 기반으로 데이터를 서버에 저장하여 아래 조건을 만족해야 한다.

- Chrome에서 작성한 데이터가 Edge에서도 조회 가능
- 다른 PC에서도 동일 계정으로 로그인하면 데이터 조회 가능
- 모바일 브라우저에서도 동일 계정으로 로그인하면 데이터 조회 가능
- 브라우저 캐시/Local Storage 삭제 후에도 데이터 유지
- 로그아웃 후 다시 로그인해도 이전 데이터 유지

# 2. 인증 방식

## 2.1 회원가입

사용자는 아래 정보를 통해 계정을 생성한다.

필수 입력값:

- 이메일
- 비밀번호
- 비밀번호 확인

### 정책

- 이메일은 사용자 계정의 고유 식별자로 사용한다.
- 동일 이메일 중복 가입은 허용하지 않는다.
- 비밀번호는 원문으로 저장하지 않는다.
- 인증 서비스에서 안전하게 hash 형태로 관리한다.
- 회원가입 완료 후 로그인 상태로 진입한다.

---

## 2.2 로그인

필수 입력값:

- 이메일
- 비밀번호

로그인 성공 시:

1. 인증 완료
2. 해당 사용자 계정의 `user_id` 확인
3. `user_id`에 연결된 지원 내역 불러오기
4. 지원 내역 메인 화면으로 이동

---

## 2.3 로그아웃

- 상단 사용자 메뉴에서 로그아웃 가능
- 로그아웃 시 인증 세션 종료
- 사용자 데이터는 삭제하지 않음
- 재로그인 시 기존 데이터 그대로 복원

---

## 2.4 비밀번호 찾기 / 재설정

기존 비밀번호를 사용자에게 직접 보여주는 기능은 구현하지 않는다.

### UX

로그인 화면 하단:

`비밀번호를 잊으셨나요?`

클릭 시:

1. 가입 이메일 입력
2. 이메일로 비밀번호 재설정 링크 발송
3. 사용자가 새 비밀번호 입력
4. 비밀번호 변경 완료
5. 로그인 화면으로 이동

### 주의

- 비밀번호 원문 조회 기능 금지
- 이메일 소유권 확인 후 재설정만 허용
- 아이디는 이메일 자체이므로 별도의 `아이디 찾기` 기능은 MVP에서 제외

# 3. 백엔드 / DB 방향

## 3.1 권장 구조

현재 Git 기반으로 코드 배포를 하고 있으므로 Git 저장소 자체를 DB로 사용하는 방식은 사용하지 않는다.

권장 구조:

- GitHub: 소스 코드 및 버전 관리
- Vercel 또는 현재 배포 환경: 프론트엔드 배포
- Supabase: 사용자 인증 + 데이터베이스
- Claude: 코드 구현 및 수정 보조

즉, 기존 Git 기반 개발 흐름은 유지하면서 **외부 DB 서비스만 추가 연결**한다.

### 데이터 흐름

```text
사용자 브라우저
    ↓
배포된 웹앱
    ↓
Supabase Auth
    ↓
Supabase Database
```

---

## 3.2 Supabase 사용 이유

2차 개발에서는 직접 백엔드 서버를 새로 구축하는 대신 Supabase 사용을 우선 권장한다.

활용 범위:

- 이메일 회원가입
- 이메일 로그인
- 비밀번호 재설정
- 사용자 세션 관리
- 사용자별 DB 저장
- Row Level Security 적용

# 5. 서류 전형 상태값 상세 정책

## 5.1 서류 확인 상태

`서류 확인`은 **서류 전형에서만 사용 가능한 상태값**이다.

### 동작

사용자가 서류 상태를 `서류 확인`으로 변경하면:

- 현재 날짜/시간을 `document_checked_at`에 자동 저장
- 상세 화면에서 확인 가능
- 사용자가 직접 날짜 수정 가능

예:

```text
지원일        2026.09.01
서류 확인     2026.09.04
서류 합격     2026.09.08
```

---

## 5.2 상태 변경 날짜 기록

상태 변경 시 날짜는 기존 MVP 정책을 유지한다.

### 예시

`예정 → 서류 확인`

- `document_checked_at = 변경 시점`

`결과대기 → 합격`

- `result_at = 변경 시점`

`결과대기 → 불합격`

- `result_at = 변경 시점`

### 수정

자동 저장된 날짜는 상세 페이지의 수정 기능을 통해 수정할 수 있다.

# 6. 기존 Local Storage 데이터 마이그레이션

2차 개발에서 매우 중요한 기능이다.

기존 사용자 데이터가 브라우저 Local Storage에 남아 있는 경우, 로그인 시스템 도입 후 기존 데이터가 사라진 것처럼 보이면 안 된다.

## 6.1 최초 로그인 후 감지

로그인 직후:

1. Local Storage에 기존 지원 데이터가 존재하는지 확인
2. 기존 데이터가 존재하면 안내 표시

예시:

```text
기존 브라우저에 저장된 지원 기록 28건을 발견했습니다.

현재 계정으로 가져오시겠습니까?

[가져오기] [건너뛰기]
```

---

## 6.2 가져오기

`가져오기` 선택 시:

- Local Storage 데이터를 현재 로그인한 사용자 계정으로 업로드
- 각 Application에 현재 `user_id` 연결
- Stage 데이터 포함하여 DB에 저장
- 성공 완료 안내 노출

예:

```text
28개의 지원 기록을 계정으로 가져왔습니다.
```

---

## 6.3 중복 방지

Local Storage 데이터를 여러 번 가져오는 문제를 방지해야 한다.

권장 방식:

- 기존 record ID 유지 가능 시 비교
- 또는 migration 완료 플래그 저장
- 동일 데이터 재업로드 방지

---

## 6.4 마이그레이션 완료 이후

마이그레이션 성공 후:

- 서버 DB를 기본 저장소로 사용
- Local Storage는 선택적으로 캐시 또는 임시 저장에만 사용
- Local Storage를 source of truth로 사용하지 않음

---

# 11. 중복 지원 정책

기존 정책 유지.

동일 기업명이 존재하는 경우 신규 등록 과정에서 경고한다.

예:

```text
동일 기업 지원 이력이 있습니다.

토스
Product Manager
2026.05.24
서류 불합격

[취소] [계속 등록]
```

등록 자체는 제한하지 않는다.

---

# 12. 합격률 계산

기존 정책 유지.

합격률은 **해당 단계 결과가 확정된 건만 분모에 포함**한다.

예:

```text
서류 결과 확정 10건
서류 합격 4건

서류 합격률 = 40%
```

`예정`, `서류 확인`, `결과대기` 상태는 결과 확정 전이므로 분모에서 제외한다.

`지원철회` 역시 합격률 계산에서 제외하는 것을 기본 정책으로 한다.

# 14. 향후 3차 개발 후보

# 15. Git / VS Code / Claude 기준 개발 진행 권장 순서

## Step 2. Supabase 프로젝트 생성

Supabase에서 신규 프로젝트 생성.

준비 항목:

- Project URL
- anon public key

환경변수로 관리한다.

```env

VITE_SUPABASE_ANON_KEY=
```

또는 사용 중인 프레임워크 규칙에 맞춰 작성한다.

### 주의

- 환경변수 파일은 Git에 커밋하지 않는다.
- `.gitignore` 확인
- 배포 서비스에도 동일 환경변수 등록

## Step 5. RLS 설정

# 16. Claude 구현 시 중요 지시사항

Claude에게 아래 원칙을 함께 전달한다.

```text
기존 1차 MVP UI와 기능을 최대한 유지한다.

전체 구조를 새로 만드는 리팩터링보다
기존 코드에 2차 기능을 확장하는 방식으로 구현한다.

특히 아래 기능은 기존 동작을 깨뜨리지 않는다.

- 지원 기록 CRUD
- 사용자 정의 전형 단계
- 단계 순서 변경
- 날짜 자동 기록
- 합격률 계산
- 중복 기업 안내
- 검색 및 필터
- 상세 페이지 수정

Local Storage 데이터는 바로 삭제하지 말고,
기존 사용자가 로그인 후 서버 계정으로 가져올 수 있도록
1회 마이그레이션 기능을 구현한다.

인증 및 DB는 Supabase 사용을 우선한다.

Git 저장소를 사용자 데이터 저장소로 사용하지 않는다.

비밀번호 원문 저장 또는 조회 기능을 만들지 않는다.

사용자 데이터는 반드시 user_id 단위로 분리하고
Row Level Security를 적용한다.
```

# 17. 완료 기준

2차 개발 완료 조건:

- 동일 이메일 계정으로 다른 브라우저에서 로그인 가능
- 동일한 지원 내역 조회 가능
- 한 브라우저에서 수정한 데이터가 다른 브라우저에서도 반영됨
- Local Storage에 있던 기존 지원 기록을 계정으로 이전 가능
- 서류 단계에서만 `서류 확인` 선택 가능
- 서류 확인일 자동 기록 및 수정 가능
- 단계별 합격률 계산이 정상 동작
- 다른 사용자의 지원 데이터 접근 불가
- 로그아웃/로그인 후 데이터 유지
- Git push 후 기존 배포 환경에서 정상 실행
