- 최종 갱신: 2026-09-14
- 대상 코드: 이 저장소 루트 (배포: GitHub Pages, `main` 브랜치)
- 현재 릴리스: v0.6.0

이 문서는 2026-09-03 ~ 2026-09-10 사이에 작성된 6개의 개별 PRD를 하나로 합친 **현행 스펙 단일 문서**다.
과거 PRD 원본은 [docs/archive/](archive/)에 시점별로 보존되어 있으며, 이 문서와 충돌하면 **이 문서가 우선**한다.

## 1. 서비스 정의

| 항목 | 내용 |
|---|---|
| 서비스명 | 줍줍 (영문: JOOB) |
| 캐치 문구 | 지원하는 오늘이, 더 좋은 내일로. |
| 한 줄 정의 | 지원한 기업·포지션·전형 진행 상황을 한곳에 기록하고, 전형별 통과율과 지원 추이를 확인하는 개인용 취업 지원 관리 서비스 |
| 사용자 | 개인 구직자 (계정별 데이터 완전 분리) |
| 기준 화면 | PC 웹 우선, 모바일에서도 정상 동작 |
| 메인 진입 화면 | 지원 내역 목록 |

### 해결하려는 문제

1. 총 몇 개 기업에 지원했는지 한눈에 보기 어렵다.
2. 동일 기업 과거 지원 이력을 놓친다.
3. 기업마다 전형 단계·순서가 달라 일관된 기록이 어렵다.
4. 전형별 진행일·결과일을 따로 기억하기 어렵다.
5. 어느 단계에서 통과율이 낮은지 파악하기 어렵다.

## 3. 인증 및 데이터 정책

- 이메일 + 비밀번호 회원가입 / 로그인 / 로그아웃 (Supabase Auth).
- 비밀번호 재설정: 로그인 화면의 "비밀번호를 잊으셨나요?" → 메일 링크 → 새 비밀번호 설정 폼.
- 비밀번호 변경: 설정 탭.
- **모든 데이터는 서버(Supabase) 우선 저장.** 저장 성공/실패는 상단바의 저장 상태 표시로 알린다.
- **사용자별 데이터 분리는 RLS로 강제한다.** `applications`는 `auth.uid() = user_id`, `stages`는 소유 application을 통한 EXISTS 검사. 프런트 필터링에만 의존하지 않는다.
- v1 시절 localStorage 기록은 최초 로그인 시 감지해 1회 가져오기를 제안하고, 완료 후 `jat_migrated_v2` 플래그로 재제안하지 않는다.

## 5. 전형 카테고리와 상태 체계

### 5.1 카테고리 (8종)

`DOCUMENT`(서류) · `FIRST_INTERVIEW`(1차 면접) · `SECOND_INTERVIEW`(2차 면접) · `ASSIGNMENT`(과제 전형) · `EXECUTIVE_INTERVIEW`(임원 면접) · `COMPENSATION`(처우 협의) · `FINAL_RESULT`(최종 결과) · `CUSTOM`(직접 입력)

- 기본 템플릿: 서류 → 1차 면접 → 과제 전형 → 임원 면접 → 최종 결과
- 단계는 추가·삭제·순서 변경 가능. `CUSTOM`만 이름을 직접 입력한다.
- 통계는 이름이 아니라 **카테고리 기준**으로 집계하므로, 자유 입력 이름이 통계를 흩뜨리지 않는다.

### 5.2 카테고리별 상태 세트

| 그룹 | 대상 | 상태값 |
|---|---|---|
| document | 서류 | 접수완료 / 서류 확인 / 결과 대기 / 통과 / 탈락 / 철회 |
| general | 1차·2차·임원 면접, 과제, 처우 협의, 직접 입력 | 진행 전 / 결과 대기 / 통과 / 탈락 / 철회 |
| final | 최종 결과 | 결과 대기 / 최종 합격 / 최종 탈락 / 철회 |

카테고리를 바꿨을 때 현재 상태가 새 세트에 없으면 기본 상태로 되돌리고 결과일·서류 확인일을 비운다.

### 5.3 날짜 자동 기록

- 상태를 통과 / 탈락 / 최종 합격 / 최종 탈락으로 바꾸면 `result_at = 오늘`. 그 외 상태로 되돌리면 결과일을 비운다.
- 상태를 "서류 확인"으로 바꾸면 `document_checked_at = 오늘`. 접수완료·진행 전으로 되돌리면 비운다.
- 자동 기록된 날짜는 사용자가 언제든 직접 수정할 수 있다.
- 날짜 역전(전형일 < 지원일, 결과일 < 전형일)은 저장을 막지 않고 경고만 띄운다.

### 5.4 자동 상태 전환

앱 로드 시 잠금 해제된 단계에 한해 실행하며, 변경 건은 `status_change_source = 'automatic'`으로 기록한다.

| 조건 | 전환 |
|---|---|
| 서류 · "서류 확인" · 서류 확인일 + 3일 경과 | → 결과 대기 |
| 면접 계열 · "진행 전" · 전형 진행일이 오늘 이전 | → 결과 대기 |

**자동으로 통과·탈락을 판정하지 않는다.** 결과 판정은 항상 사용자 입력이다.

## 6. 단계 잠금 로직

- 첫 단계는 항상 열려 있다.
- **N번째 단계는 N-1번째 단계가 "통과"일 때만 수정 가능하다.** 잠긴 단계는 상태·날짜·메모·이름 변경이 모두 차단된다.
- 앞 단계 결과를 통과 → 탈락으로 되돌리면 뒤 단계는 **데이터를 지우지 않고 잠그기만** 한다. 다시 통과로 바꾸면 기존 입력값이 그대로 살아난다.

### 현재 단계 계산

`order_index` 순으로 훑으며 "통과"면 다음으로 넘어가고, 통과가 아닌 첫 단계가 현재 단계다. 전부 통과면 마지막 단계.

### 지원 건 전체 상태

| 상태 | 조건 |
|---|---|
| 종료 | 철회 또는 탈락 단계가 있거나, 마지막 단계가 최종 합격/최종 탈락 |
| 진행중 | 그 외 |

## 7. 화면 구성

상단바(저장 상태 · 기록 추가 · 계정 메뉴) + 좌측 사이드바(지원 내역 / 통계 / 캘린더 / 메모 / 설정 / 도움말) + 콘텐츠. **동일 메뉴를 상단바와 사이드바에 중복 배치하지 않는다.**

### 7.1 지원 내역 (메인)

- 상단 KPI 4종 + 필터바(기업명 검색, 지원 상태, 전형 상태, 현재 단계, 포지션, 초기화).
- 테이블 컬럼: 기업명 · 지원 포지션 · 지원일 · 현재 단계 · 전형 상태 · 최근 일정 · 메모.
- 목록에서는 수정하지 않는다. 모든 편집은 상세 페이지에서.
- 최근 일정은 아직 결과가 나오지 않은 단계 중 가장 이른 진행일.

### 7.2 상세

기업 정보 수정 / 삭제, 좌측 전형 타임라인(카테고리·상태·날짜·메모·순서 이동·추가·삭제), 우측 기업 메모. 모든 변경은 즉시 자동 저장.

### 7.3 통계

1. **전체 지원 현황** — KPI 4열
2. **월별 지원 추이** — 최근 3개월 라인차트 + 전월 동기간 대비 증감
3. **전형 통과율** — 서류 / 1차 면접 / 2차 면접 / 과제 전형 / 임원 면접, 그리고 최종 합격률
4. **전형 소요시간** — 카테고리별 평균 일수
5. **지원 포지션 분석** — 포지션별 지원 수와 서류 통과율

계산 기준:

- 통과율 = 통과 ÷ (통과 + 탈락) × 100. 진행 중·철회 건은 분모에서 제외.
- 최종 합격률 = 최종 합격 ÷ (최종 합격 + 최종 탈락) × 100.
- 소요시간: 서류는 `지원일 → 결과일`, 그 외 전형은 `전형 진행일 → 결과일`의 평균. 음수는 제외.
- 데이터가 없으면 0%가 아니라 "데이터 없음"으로 표기한다.
- 포지션은 자유 입력이며 자동 정규화하지 않는다. (표준화는 향후 과제)

### 7.4 캘린더 / 메모 / 설정 / 도움말

- 캘린더: 월 단위, 지원일·면접·과제·기타 전형을 색으로 구분.
- 메모: 기업 메모 또는 전형 메모가 있는 지원 건만 모아 보기.
- 설정: JSON 내보내기/가져오기, 비밀번호 변경, 계정 전체 삭제.
- 도움말: 현행 동작 기준 안내 (2026-09-14 기준 최신화 완료).

## 8. 중복 지원 감지

기록 추가 시 기업명이 기존 기록과 일치하면 과거 지원 이력을 안내한다. **경고일 뿐 저장은 항상 허용한다.** 동일 기업 다른 포지션, 동일 기업 재지원 모두 별도 건으로 기록한다.

## 9. 업데이트 공지 모달

- `app.js`의 `RELEASE_NOTE` 상수 하나로 버전 · 일시 · 제목 · 소개 · 항목 카드를 정의한다.
- 로그인 직후 노출. "다시 보지 않기"를 누르면 Supabase user metadata의 `hidden_update_version`에 해당 버전을 저장해 그 버전은 다시 띄우지 않는다.
- "확인했어요"는 이번 세션만 닫는다. ESC로도 닫힌다.
- 새 버전을 배포할 때 `RELEASE_NOTE.version`을 올리면 전 사용자에게 다시 노출된다.
